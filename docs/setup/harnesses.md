# Connecting your AI harness

Every harness gets the same things from the repository: the rules, the MCP servers, the skills
and the subagent roles. The repository keeps one source of each in `.agents/` and in the
workspace folder, and `scripts/sync_harness.py` generates what each harness reads.

**Tested:** the rules, the skills and the guard hook were used with Claude Code. The other
harnesses were not tried: what this page says about Codex, Cursor, Gemini CLI, Antigravity and
GitHub Copilot follows their vendors' documentation and is marked "Not verified" where it stands.
If a step here does not match what you see, fix this page and send the fix to the kit
([updating.md](updating.md#send-an-improvement-back-to-the-kit)).

## Sources and generated files

| What | Source | Generated by `scripts/sync_harness.py` |
|---|---|---|
| Rules | `AGENTS.md` | nothing: `CLAUDE.md` and `GEMINI.md` import it, `.github/copilot-instructions.md` points to it |
| MCP servers | `.agents/mcp.json`, `app_url` of the registry, `mcp_servers` of `harness.json` | `.mcp.json`, `.cursor/mcp.json`, `.codex/config.toml`, `.gemini/settings.json`, `.agents/mcp_config.json` |
| Claude Code permissions and hooks | `.agents/claude-settings.json`, the two profiles of the registry, `claude_allow` of `harness.json` | `.claude/settings.json` |
| Skills | `.agents/skills/` | a copy in `.claude/skills/`; a skill that needs an optional server only while the workspace switched that server on |
| Subagent roles | `.agents/agents.json`, `.agents/roles/`, `.agents/models.json`, `models` of `harness.json` | `.claude/agents/`, `.codex/agents/` |
| The list of what was generated | every file above | `.agents/generated-files.json` |

`harness.json` is `workato/workspaces/<workspace>/harness.json`. An unknown key in it is an
error. After you edit any source, run:

```bash
scripts/sync_harness.py
```

`make check` fails while a generated file is out of date. Never edit a generated file by hand:
the next run overwrites it.

`.agents/generated-files.json` lists the files the last run wrote. When a source is gone (a
removed skill or role), the script deletes its generated file only if that list names it. A file
a person put into `.claude/agents/` or `.claude/skills/` stays, and the script prints
`left alone, not generated here: <path>`.

The Codex hook file `.codex/hooks.json` is not generated: the kit ships it as it is.

Not verified: every row but Claude Code's. They say what the vendors document; nobody has tried
them with the kit.

The guard is `scripts/guard_wk.py`. It blocks the `wk` commands of the rules **No package commands**
and **Secrets** (`wk pull`, `wk diff`, `wk clone`, `wk push`, `wk auth token`, `wk mcp auth-header`,
`wk --verbose`), shell commands that name `profiles.env`, `wk ... -o` with a file outside `tmp/`,
and `xargs wk` fed from standard input ([workato.md](workato.md#never-run-these)). It guards against
mistakes; it is not a security boundary. It recognizes the usual shell forms, also inside `sh`,
`bash`, `zsh`, `dash`, `ksh`, `fish`, `csh` and `tcsh -c` and `env -S`, but not `eval`, a command
held in a variable, text piped into a shell, a script, or a program handed to another interpreter
(`python3 -c`). Where it does not run, the rules in `AGENTS.md` are the only thing that stops such a
command. The hook needs `python3.14` on the PATH your harness sees: restart the harness after you
install Python.

## Approvals

The agents may read freely; a write to Workato needs a person. How a harness asks:

| Harness | What the kit configures | What you set |
|---|---|---|
| Claude Code | `.claude/settings.json`: an allow list of read-only `wk` commands (without `-p` and with each of the registry's two profiles), most of the kit's scripts (none of them writes to Workato), `make check`, `make test`, `make lint` and `make typecheck` (each exactly, without arguments) and a few read tools of the Workato MCP server; a deny list; the guard hook. Everything else asks or is denied, in Manual mode (see "The kit counts on Manual mode" below). | Personal additions in `.claude/settings.local.json`, which is git-ignored. Additions for the whole team in `claude_allow` of `harness.json`, then `scripts/sync_harness.py`. |
| Codex | the guard hook only | Keep Codex asking before shell commands and MCP tool calls. |
| Cursor, Gemini CLI, Antigravity, GitHub Copilot | nothing | Keep the harness asking before each shell command and each MCP tool call. Do not switch on automatic runs for this repository. |

`claude_allow` accepts only two kinds of rule: the workspace's own scripts,
`Bash(scripts/ws_<name>.py)` or `Bash(scripts/ws_<name>.py *)`, and single tools
`mcp__<server>__<tool>` of an optional server the workspace switched on. Anything else stops
`scripts/sync_harness.py` with a message that ends "Keep any other permission in your own
.claude/settings.local.json".

`scripts/sync_harness.py` itself is not on the allow list, only its `--check` form: it rewrites
the permissions of Claude Code, so a person runs it or approves the run. It prints the allow and
deny rules it adds and removes, and the MCP servers it adds and removes: read those lines before
you commit.

The allowed scripts write files of the repository and of `tmp/`: the Prod copy, the recipe
index, the lookup-table descriptions, `prod_recipe_id` in recipe docs, lint and comparison
output. Read `git diff` before you commit. Three allowed commands take an output path:
`wk recipes pull` and `wk recipes export` may write with `-o` only below `tmp/` (the guard blocks
any other path), and `scripts/prod_jobs_report.py --out` refuses a file outside `tmp/`.

**Keep edit auto-accept off in this repository.** The allow list runs the repository's own
scripts (`scripts/*.py`, `make check`, `make test`) without asking. In a mode that accepts file
edits without asking, an agent could change such a script and then run it under its allow rule,
and you would see no prompt for either step. Documented
(<https://code.claude.com/docs/en/permissions>): the answer "Yes, and don't ask again" to a file
edit holds until the session ends, so after it the same path is open in Manual mode. The same
holds for any harness that runs commands or edits files on its own.

**Do not save an approval for an interpreter or for a Workato write.** Documented
(<https://code.claude.com/docs/en/permissions>): in Claude Code the answer "Yes, and don't ask
again" saves an allow rule for the text the option shows. The allow rule goes into
`.claude/settings.local.json` and applies to later sessions of the repository. A rule matches
the text of a command, not what a program started by that command does. So read the text before
you choose the option. When it ends in `*` after an interpreter, such as `python3 -c *`, any
code runs without asking from then on, and no deny rule sees what that code does. The guard
reads shell commands, also inside `bash -c`, but not a program handed to another interpreter
(`python3 -c`, `node -e`). An approval saved for a command that writes to Workato, such as
`wk recipes start *`, lets that write run without asking from then on, and so does an allow
rule for a write tool of the Workato MCP server.
[tools.md](tools.md#how-a-workspace-adds-a-tool) says never to allow a command that changes
Workato. Choose plain "Yes" for the one run, and when your `.claude/settings.local.json`
already holds such an allow rule, remove that line.

**The kit counts on Manual mode.** "Asks" on this page means Claude Code in Manual mode
(`default` in the settings), with no saved approval for the action. Documented
(<https://code.claude.com/docs/en/permission-modes> and
<https://code.claude.com/docs/en/permissions>):

- Accept edits mode accepts file edits, and common file commands such as `rm` and `mv`, without
  asking;
- Auto mode runs without routine prompts: a classifier decides instead of a person;
- Bypass permissions mode skips the permission prompts, except for a few actions that no mode
  approves on its own, such as a tool that an `ask` rule names. Allow rules have no effect in
  it, and deny rules still block. It gives no protection against prompt injection or unintended
  actions, and the vendor says to use it only in an isolated environment, such as a container
  or a virtual machine;
- the desktop app remembers the mode picked for a folder, so check the mode selector before the
  first message;
- `permissions.disableBypassPermissionsMode` set to `disable` blocks Bypass permissions mode: an
  administrator sets it in managed settings, and a person can set it in their own settings.

In Auto mode and in Bypass permissions mode an agent can write to Workato without asking. Apart
from the few commands the deny rules and the guard catch by their text, `wk push` among them,
only the rules in `AGENTS.md` then stand between an agent and a Workato write, and the guard
guards against mistakes; it is not a security boundary. The kit recommends neither mode. A mode
shows in the session; a saved allow rule does not. Never use saved allow rules to get a session
without prompts. Observed: the guard hook runs in Bypass permissions mode too.

## Claude Code

1. **Start Claude Code in the repository root.** Claude Code loads `.claude/settings.json`, and
   with it the allow list and the guard hook, only from the folder where the session starts. A
   session started in a subfolder has neither.
2. Trust the folder when asked. The project's allow rules apply only after you accept that
   dialog.
3. Approve the project's MCP servers when asked. Switch Workato to Dev in the browser, then run
   `/mcp` and sign in to `workato-airo-mcp-server`. If the workspace switched Atlassian on, sign
   in to `atlassian` too ([atlassian.md](atlassian.md)).
4. Run `/hooks` and check that the Bash guard is listed.
5. `/agents` lists the four subagents. The skills show up in the `/` menu. The three Atlassian
   skills are there only while the workspace has the `atlassian` server switched on.
6. Read [Approvals](#approvals) before you answer the first permission prompt.

A deny rule matches the text of a command, so `Bash(wk pull *)` does not catch
`wk -p acme-dev pull` or a full path to `wk`. The guard hook catches those forms; like the deny
rules, it guards against mistakes and is not a security boundary.

## Codex CLI and the ChatGPT desktop app

Not verified: every step of this section.

1. Open the repository and mark the project as trusted. Codex ignores `.codex/config.toml`
   otherwise.
2. Switch Workato to Dev in the browser, then sign in to the server:

   ```bash
   codex mcp login workato-airo-mcp-server
   ```

   And, if the workspace switched Atlassian on:

   ```bash
   codex mcp login atlassian
   ```

3. Codex reads `AGENTS.md` and the skills in `.agents/skills/` on its own.
4. `.codex/hooks.json` runs the same guard, with the same limits. Codex skips a project hook
   until you have reviewed and trusted it: run `/hooks` once, and again whenever the hook line
   changes.
5. `.codex/agents/` holds the four roles. By default they run on the session's model with the
   effort that `.agents/models.json` sets ([skills.md](skills.md#subagent-roles-and-models)).

ChatGPT in the browser cannot read the repository's configuration. Use the desktop app or the
CLI.

## Adding an MCP server for everyone

A new MCP server needs the maintainer's yes and a line in
[decisions.md](../conventions/decisions.md) ("Integrations" in [AGENTS.md](../../AGENTS.md)).

- A server the kit already lists as optional, such as `atlassian`, is switched on in the
  workspace's `harness.json` under `mcp_servers`, then `scripts/sync_harness.py`.
- Any other server would mean editing `.agents/mcp.json`, a kit file. Propose it to the kit
  instead ([updating.md](updating.md#send-an-improvement-back-to-the-kit)).

Only remote servers with per-user sign-in belong there: no tokens, no command-line servers with
credentials in their arguments.
