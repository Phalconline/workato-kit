# Workato workspace repository: rules for AI agents

This file is the authority for how agents work here. Every harness reads it (`CLAUDE.md` and
`GEMINI.md` import it). Nothing here overrides runtime permissions, sandbox restrictions or the
policy of your organization.

"A person" below means the human you are working with. "The maintainer" is named in the registry
(`maintainer`); while that is empty, it is the person you work with. Rules are referred to by
their names, in bold.

## What this repository is

Documentation, a copy of the recipes that run in Prod, and tooling for one Workato workspace. It
holds no running automation: recipes live in Workato and are changed there, through the Workato
MCP server (`recipe_builder_*`) or the `wk` CLI.

The repository was built from a public kit. The kit owns the tooling and these rules; the
workspace owns its data and its own rules, in the last section of this file.

## Layout

Everything the repository keeps of the workspace itself is in one folder,
`workato/workspaces/<workspace>/`. There is exactly one such folder; `<workspace>` below stands
for its name. Until `scripts/init_workspace.py` has created it, the repository has no workspace
and only the offline checks work (`docs/setup/new-workspace.md`).

| Path | What it holds | Who writes it |
|---|---|---|
| `workato/workspaces/<workspace>/registry.json` | the workspace: its two `wk` profiles, every project with its ids, and the settings the scripts read | `scripts/init_workspace.py`, then by hand |
| `workato/workspaces/<workspace>/projects/<slug>/` | Prod recipe JSON and `index.json` (recipes, folders, connections, property names) | `scripts/sync_recipes.py prod` only |
| `workato/workspaces/<workspace>/message-templates/`, `connectors/`, `lookup-tables/` | workspace-level sources | templates and connectors by hand; lookup tables by `scripts/sync_lookup_tables.py`, with the purpose and field texts by hand, never data |
| `workato/workspaces/<workspace>/notes/` | what this workspace adds to a skill: one file per skill | by hand |
| `workato/workspaces/<workspace>/harness.json` | harness choices of the workspace: optional MCP servers, extra permissions, models | by hand, then `scripts/sync_harness.py` |
| `workato/workspaces/<workspace>/inventory/recipes-index.json`, `docs/recipe-index.md` | the recipe index | generated by `scripts/build_index.py` |
| `workato/workspaces/<workspace>/inventory/doc-sync.json` | when each doc was last compared with Workato | `scripts/doc_sync.py stamp` only |
| `docs/<slug>/` | docs of one Workato project: `recipes/`, `design/`, `runbooks/`, `reference/` | by hand |
| `docs/setup/`, `docs/conventions/`, `docs/knowledge/` | setup, conventions, platform notes | the kit; the workspace's own decisions go to `docs/conventions/decisions.md`, its own notes to `docs/knowledge/workspace/` |
| `scripts/`, `tests/`, `Makefile`, `pyproject.toml` | tooling in Python and its offline checks: `make check` | the kit; a workspace adds its own as `scripts/ws_*.py` with `tests/test_ws_*.py` |
| `.agents/` | skills, subagent roles and the sources of every harness file | the kit, then `scripts/sync_harness.py`; a workspace adds its own skill as `.agents/skills/ws-<name>/` |
| `tmp/` | your personal working cache; git-ignored | you; see "Working cache" |

## Environments and ids

- **Dev** is where every recipe change is made. **Prod** changes only by deployment from Dev.
  The registry knows these two environments and no other.
- Project ids, folder ids and the `wk` profile of each environment come from the registry:
  scripts read them only from there, and where a doc and the registry disagree, the registry is
  right. `WK_PROFILE_DEV` and `WK_PROFILE_PROD` override the profile names for scripts.
- The Workato MCP server acts in the environment that was active in the browser when you
  authorized it. Authorize it for Dev.
- A recipe has a different id in each environment. Repo docs are named with the **Dev** id and
  carry `prod_recipe_id` in their frontmatter; `workato/workspaces/<workspace>/projects/` uses
  **Prod** ids. The two copies are paired by `match_key` (folder plus name) in the `index.json`
  files.
- A project with `"snapshots": true` in the registry is a **managed project**: it exists in Dev
  and Prod, and its Prod recipes are copied into the repository. Any other project is in Dev only.

## Rules without exceptions

### Writing to Workato

- **Change only what was asked.** Change Workato only when the request asks for that change.
  Editing a recipe in Dev that the task names needs no further confirmation. Starting, stopping
  or deleting anything, and any write in Prod, need the request to say so in words. If an edit
  needs a stop first, say what the stop does and ask, unless the request already covers it.
  Discussion alone is not a request to execute. Say what you changed in the same message.
- **Prod changes only by deployment.** Change the recipe in Dev, then deploy the project to Prod
  when a person asks for that deployment. Never edit a Prod recipe directly: a direct edit is
  drift, and the next deployment overwrites it. Load `workato-prod-deploy`.
- **No package commands.** Never run `wk pull`, `wk diff`, `wk clone` or `wk push`. The first
  three create a new export manifest in Workato on every run and never delete it; `wk push`
  imports a whole package. `scripts/sync_recipes.py` and `wk recipes pull <id>` are plain GETs.
  Do not "correct" the scripts back to the package flow. `scripts/guard_wk.py` blocks the four
  commands where a harness runs it as a hook; where none does, this rule is the only guard. The
  hook guards against mistakes; it is not a security boundary.
- **Push procedure.** Pull a fresh recipe as the base of every change. Right before the push,
  read the remote recipe again and compare it with that base; if it changed, pull again and
  reapply your edits. Do not push while a person is editing that recipe in the UI. After the
  push, verify the saved recipe, lint it and report. Load `workato-recipe-edit`.
- **One writer.** Write to Workato from the main conversation only, one recipe at a time. Never
  from a subagent: a harness may run it in the background, where a relayed chat message can
  redirect it in the middle of a write.
- **Check the project first.** Read a recipe's project id before its first edit: a name or a
  prefix does not tell you which project a recipe is in. Lint and doc location depend on the
  project.
- **A running recipe is locked.** Workato refuses every change to it: stop, edit, verify, start
  again. A stop strands callers, so say what it does in the same message: a call to a stopped
  recipe function fails and does not queue, a polling trigger parks its cursor, a webhook trigger
  may lose events, a schedule does not run while its recipe is stopped. Start callees before
  callers. Load `workato-start-stop`.
- **No jobs on your own.** Never start a recipe only to produce a test job and never repeat a
  job, unless a person asked for that run. Build, verify from the raw JSON, then ask.
- **Nothing destructive in silence.** Delete an asset or disconnect a connection only when the
  request says so, and first find what depends on it and say what is destroyed. Load
  `workato-assets`.
- **Connections stay in reach of a deployment.** Bind a recipe only to a connection of its own
  project or of the project the registry marks `shared_connections`. Observed: a deployment
  leaves the Prod slot of any other connection empty.
- **Secrets.** Never type a password, API key, token or client secret. A person enters
  credentials in the Workato UI, in `wk auth login`, or in `profiles.env`. Never read a secret
  from a property, a connection or `profiles.env` to reuse or show it. Never run `wk auth token`
  or `wk mcp auth-header` in a shell, in any form: both print the API token, and a pipe, a
  substitution or a redirect puts it into the transcript. Never run `wk --verbose`: a debug log
  may show the request headers. For an API call that `wk` does not cover use
  `scripts/wk_api.py`: it reads the token inside its own process.
- **Comments and descriptions belong to people.** Never rewrite an existing step comment or a
  recipe description a person wrote. Adding a comment to a step that has none is fine. If an
  existing one went stale, say so in chat with the current text and a suggested replacement.
- **A description describes.** A recipe description says what the recipe does. It holds no test
  notes, no release to-dos and no run-state notes such as "Not run yet". Neither a description
  nor a step comment, a comment inside a code step included, compares the recipe with an older
  version or with a system it replaced: that history belongs in the repository docs.
- **A recipe has a Jobs view.** A new recipe gets a job report (the custom columns of its Jobs
  tab) in the same push as its steps: what the job is about and how it ended, chosen for that
  recipe alone. After every edit, review the columns against the changed recipe and fix them in
  the same task. `docs/conventions/job-view.md` says how.
- **Sensitive data stays out of job history.** Every step whose input or output holds a
  credential (a password, a passcode, a token, an API key, a client secret) has "Mask data" on:
  the step that creates or reads the value and every step it is passed to. A credential never
  goes into a step that sends it where a mask does not reach: a chat or e-mail message, a logger
  step, a job report column, the result a recipe function returns, or the `message` of a `catch`
  (send the error type or the HTTP status instead). A credential a person receives by design,
  such as a temporary password in an activation e-mail, is the one exception, and the recipe doc
  names it. A step that receives or returns personal data of people outside the organization (a
  customer, a lead, a website visitor) is masked too, unless the recipe doc says why it stays
  readable. Set the masks in the same push as the steps, list the masked steps in the recipe
  doc, and never remove a mask a person set unless the request says so.
  `docs/conventions/data-masking.md` has the platform facts.

### Repository

- **Generated files are never edited by hand.** In `workato/workspaces/<workspace>/`:
  `projects/<slug>/`, `inventory/recipes-index.json` and `inventory/doc-sync.json` (written by
  `scripts/doc_sync.py stamp`). Elsewhere: `docs/recipe-index.md`, and
  the harness files that `scripts/sync_harness.py` writes: `.claude/settings.json`,
  `.claude/skills/`, `.claude/agents/`, `.codex/agents/`, `.codex/config.toml`,
  `.cursor/mcp.json`, `.gemini/settings.json`, `.mcp.json`, `.agents/mcp_config.json` and
  `.agents/generated-files.json`. The two vendor skills are pinned copies: change them only by
  the update procedure in `docs/setup/skills.md`.
- **No secrets and no table data in the repository.** Connection names and pointers only. No
  rows of lookup tables or data tables.
- **Real people stay out.** Job titles and error texts can hold personal data, such as the
  e-mail address of a customer or a user: never copy one into a tracked file, write `<user>`.
  Docs give dates of runs, never run counts.
- **Keep the Prod copy true.** After every deployment, and after any other change in Prod, run
  `scripts/sync_recipes.py prod` and commit the result with the doc changes. Before a deployment
  run it with `--check`. If it reports a difference, refresh the copy and read
  `git diff workato/workspaces/` next to the deployments since the last sync
  (`scripts/wk_api.py dev GET /deployments -q project_id=<dev project id>`). A change in a
  recipe's code, bindings, name or description, or a recipe added or removed, that no deployment
  explains is a direct Prod edit: stop and port it to Dev first, or get a person's word to drop
  it; otherwise the deployment overwrites it. A change only in `running`, `version` or a
  connection's `authorized` flag is a missed sync: commit the refreshed copy and go on.
- **Kit files hold no workspace data.** An id, an address, a host or a name of this workspace
  never goes into a file the kit owns: every file that is not the workspace's own
  (`docs/setup/updating.md` has the table). It goes into the registry, into `notes/`, into
  `docs/<slug>/` or into the last section of this file. `scripts/check_kit_files.py`, part of
  `make check`, catches ids, addresses, hosts, bracket codes, ticket keys, dates and the names
  the registry holds. It cannot know every name, a recipe's or a connection's for example: read
  a change to a kit file before it leaves this repository.

### Documentation

- **Never invent recipe behavior.** If a recipe's logic was not read from its JSON or the Workato
  UI, set `verified: unverified` in the doc and say what is assumed.
- **One doc per recipe**, at `docs/<project-slug>/recipes/<dev_recipe_id>-<kebab-name>.md`, under
  the Workato project the recipe sits in, from `docs/conventions/recipe-doc-template.md`.
- **A recipe doc has no step numbers**, no bare id for a called recipe (name as a link, call
  type, fields passed) and no provenance line. `make check` fails on a step number
  (`scripts/check_step_numbers.py`). Load `recipe-docs`.
- **A decommission proposal states the blast radius** (who calls the recipe) before the
  recommendation.
- **Sync the docs around a recipe.** Before you read a recipe for a change, a review or a
  decommission proposal, run `scripts/doc_sync.py plan <dev recipe id>`. It lists the recipe,
  what it calls, its connections, its lookup and data tables, and the recipes that call it or
  share one of those tables. An asset is stale when its doc was never synced, was synced more
  than 24 hours ago, or the asset changed in Workato since. For each stale one compare the doc
  with the live asset, fix the doc and set `last_reviewed`; then run `scripts/doc_sync.py stamp`
  for what you really compared, and for nothing else. More than 15 assets in the plan: do not
  refresh them all on your own, pick the ones the change touches or ask the person. A recipe you
  pushed is compared and stamped again in the same task. Load `recipe-docs`.

## Which skill to load

Skills are in `.agents/skills/<name>/SKILL.md`. Load the one that matches before you act. Each
skill of the kit points at `workato/workspaces/<workspace>/notes/<name>.md`: when that file
exists, read it too. It holds what this workspace adds to the procedure.

| Task | Skill |
|---|---|
| Check which environment the CLI and the MCP server act in (first write of a session, after a sign-in) | `environment-preflight` |
| List what a change, a deployment or a decommission touches | `change-impact-review` |
| Build or test a custom connector | `connector-development` |
| Change a recipe in Dev (build, edit, push, lint) | `workato-recipe-edit` |
| Stop or start a recipe | `workato-start-stop` |
| Connections, tags, data tables, deleting anything | `workato-assets` |
| Deploy a project to Prod | `workato-prod-deploy` |
| Read recipe JSON, refresh the Prod copy, check for drift | `workato-recipe-json` |
| Job history, failed jobs, logs | `workato-job-history` |
| Write or update a recipe doc in this repo, or refresh the docs around a recipe (`doc_sync.py`) | `recipe-docs` |

Three more skills serve a team that uses Jira and Confluence, and apply only when the workspace
switched the Atlassian server on in `harness.json`: `confluence-recipe-pages` (pages about
recipes), and the vendor skills `search-company-knowledge` and `triage-issue`. Recipes, rules and
decisions are answered from this repository first.

A skill of the workspace's own is named `ws-<name>` and listed in the last section of this file.

## Working cache (`tmp/`)

`tmp/` is yours alone. It is git-ignored, so nobody else has your files and you have nobody
else's.

- Put every temporary thing there and nowhere else in the tree: raw pulls, before and after
  copies for a push, job dumps, lint output, findings of a review, drafts. Scripts already do:
  `tmp/wk/dev/<slug>/` is the Dev recipe JSON, `tmp/wk/` holds lint and comparison output. The
  hook lets `wk ... -o <file>` write only below `tmp/`.
- Use `tmp/<area>/<YYYY-MM-DD>-<topic>/` for a piece of work.
- Never link to a file under `tmp/` from a tracked file, and never rely on one being there: it
  may be missing or stale. `scripts/check_links.py` fails on such a link.
- When a result matters to the team, write the conclusion into `docs/` and leave the raw
  material in `tmp/`.
- It can hold personal data from jobs. Nothing from it is committed or pasted into a doc
  without redaction.
- What a script can rebuild (`tmp/wk/`) is safe to delete. Anything else in `tmp/` may be
  someone's only copy: ask before deleting it. `tmp/README.md` is the only tracked file in it.

**Reserved file names.** Never name a file `CLAUDE.md`, `AGENTS.md` or `GEMINI.md`, in any
letter case, in `tmp/` or anywhere else below the repository root. Some file systems ignore
case, and a harness loads a file with such a name as instructions for its folder, whatever it
holds. For the same reason a full copy of the repository goes outside this tree.

## Before you finish

- After a push to a recipe of a managed project: `scripts/lint_recipes.py --recipe <dev_recipe_id>`.
  For a project that was never deployed, name it: `scripts/lint_recipes.py <slug>`.
- After working on a recipe: `scripts/doc_sync.py plan <dev_recipe_id>` shows nothing stale. The
  whole repository: `scripts/doc_sync.py status`.
- After a deployment, or any other change in Prod: `scripts/sync_recipes.py prod`, then
  `scripts/link_prod_ids.py` (when a recipe is new to Prod, refresh the Dev copies first:
  `scripts/sync_recipes.py dev`).
- After the first deployment of a project: the registry has no Prod ids for it yet, so its Prod
  recipes are not copied. A person runs `scripts/init_workspace.py` again with the same
  arguments (it adds the Prod ids), then `scripts/sync_recipes.py prod`.
- After editing Markdown: `scripts/check_links.py`. After editing a recipe doc also
  `scripts/check_step_numbers.py`.
- After editing a skill, a role, a model choice, `harness.json` or a source in `.agents/`:
  `scripts/sync_harness.py`. It rewrites the permissions of Claude Code, so a person runs it or
  approves the run.
- After editing a script or a test: `make format`, then `make check` (offline; CI runs the same
  command). Both need `make dev` once: it installs Ruff and mypy into `.venv/`. A script follows
  `docs/conventions/python.md` and has its tests in `tests/test_<script>.py`.
- Scripts and hooks run on `python3.14`, any patch release, and use the standard library only.
- Setup problems: `scripts/doctor.py`, then `docs/setup/README.md`.
- Merging an update of the kit, removing or renaming a project, a new maintainer:
  `docs/setup/updating.md` and `docs/setup/maintaining.md`.

## Integrations

- The tools of this repository are the `wk` CLI, the MCP servers in `.agents/mcp.json` and the
  connectors your harness already provides. `wk` is a Workato Labs tool, published without an
  SLA; the procedures here use it for stop and start, lint, tags and recipe JSON.
- The tooling needs no server and no app of its own.
- A new tool or MCP server needs the maintainer's yes and a line in
  `docs/conventions/decisions.md`. A skill grants no credentials and no permission to write to
  an external system.

Why each rule exists is in `docs/conventions/rationale.md`.

## Rules of this workspace

The kit ships this section empty. A workspace writes its own rules here, and only here, so that
an update of the kit never conflicts with them. They add to the rules above and win where they
are stricter. Write a rule like the ones above: a name in bold, then what to do. Its reason goes
to `docs/conventions/decisions.md`. Typical entries: a recipe that must stay stopped, who must
be asked before a start in Prod, a project that is never deployed, the workspace's own skills
(`ws-<name>`) and when to load each.
